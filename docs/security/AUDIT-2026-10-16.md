# Security review — 16 October 2026

This is a repository review of wallet-mcp (`btc-wallet-mcp` 0.2.0) on `main` at `80fdd63`, plus the fixes made in the same change. It is **not** a substitute for an independent professional audit. A green CI run is not one either. Do not put funds you cannot lose on a hot wallet this software controls.

Reviewed surfaces: the payment gate and HMAC approval, seed storage, spend limits, chain HTTP clients, the configure UI, address and amount checks, mainnet opt-in, and the supply-chain files in `.github/`. No transaction was broadcast. The integration test stays opt-in and was not run.

This branch was later rebased onto a newer `main`. That `main` added USDC/USDT, Solana, XRP destination tags, owner-side hardware signing, `scripts/install.sh`, and `deploy/`. Those changes are kept. Solana RPC and the approval webhook use the same redirect-refusing client as the other URL fetchers. A token payment reserves its gas on the parent coin's sealed ledger before broadcast. The findings below were made against `80fdd63`. The later features were not a separate full review.

A later change added an owner-granted autonomous budget (`auto_max_per_tx`, `auto_max_per_day`, `auto_mac`). It was not part of the 16 October review. The control is described in [SECURITY.md](../../SECURITY.md) and [docs/auto-budget.md](../auto-budget.md). Payments inside that budget can be broadcast from `prepare_payment` without a per-payment HMAC. Everything above it still needs one. Cold wallets never auto-spend. A tampered `auto_mac` fails closed.

## How this maps to the requested standards

**OpenSSF Scorecard-style checks.** `SECURITY.md` already existed and now points here. Workflows declare `permissions: contents: read`. `actions/checkout` and `actions/setup-python` are pinned to commit SHAs. Gitleaks 8.28.0 is installed from a checksummed tarball so the workflow does not need `security-events: write`. Dependabot updates pip and GitHub Actions weekly. Semgrep, bandit, ruff (rule set `S`), pip-audit, and gitleaks run in `.github/workflows/security.yml`. Branch protection cannot be set from the repository. There are no signed releases and no signing key in this change. Python dependencies stay as version ranges; hash pins were not invented, because a wrong multi-platform hash set would break installs. Dependabot and pip-audit are the mitigation.

**OWASP ASVS (relevant chapters, not a full ASVS certification).** Approval codes are compared in constant time, confirm ids are single-use with a 600-second TTL, and five failures lock the coin. Cold wallets cannot sign. Mainnet is opt-in. Seeds are encrypted at rest and are not MCP tool results. Data directories are mode `0700`. The configure UI is bound to localhost, checks `Host` and `Origin`, and sends a restrictive `Content-Security-Policy`.

**OWASP Top 10 for LLM applications.** Prompt injection does not become a payment: `send_payment` needs a human HMAC over the confirm id, address, amount, and fee. The agent does not receive the approval secret or the passphrase through a tool. The gate is the only spend path (`ChainAdapter.execute` is not for adapters to override). Limits are reserved under a file lock before broadcast.

**SLSA.** The build is GitHub Actions with pinned actions and read-only token permissions. There is no provenance attestation and no signed artifact. This is not a SLSA level claim.

**CWE.** The high and medium findings below cite the CWE that matches the bug. Bandit's B310 label (CWE-22) is the scanner's id for `urlopen`; the issue as used here is CWE-918.

## Critical

None found.

## High

### H1 — Approval screen could be rewritten with control and bidi characters

**CWE-150.** The memo and the address were shown to the human as-is. A memo or address containing newlines, ANSI escapes, or Unicode bidi / format characters (`Cf`) could make the terminal show a different destination or amount than the one covered by the HMAC.

**Fix.** `assert_safe_address` allows ASCII only, rejects whitespace and controls, and caps length at 256. Trailing whitespace is stripped, so a trailing newline is not a bypass; an embedded newline is rejected. `assert_safe_memo` caps the memo at 140 characters and rejects C0, DEL, and category `Cf`. There is no silent truncation. The CLI also runs `sanitize_terminal` so an old pending row cannot redraw the screen.

### H2 — Concurrent sends could pass the daily limit

**CWE-362.** The 24-hour total was read, then the payment was broadcast, then the ledger was updated. Two approvals racing could both observe the same total and both broadcast.

**Fix.** `Policy.authorize_and_reserve` holds `fcntl.flock` across the pending-state read, code check, total check, and ledger append. The row is written with an empty txid **before** broadcast, so the amount is already in the window. `attach_txid` fills the txid after a successful broadcast. A failed broadcast still consumes the daily budget and the confirm id (fail closed). If attaching the txid fails after a broadcast that succeeded, the error is logged and the send still returns success, so the caller does not retry a payment that already went out.

The 24-hour window is `time.time()` epoch seconds (UTC), not a local calendar day. A timestamp in the future still counts, because the check is `ts >= now - 86400`.

### H3 — A Bitcoin WIF was accepted as a watch-only descriptor

BDK's descriptor parser accepts `wpkh(<WIF>)`. `str(descriptor)` redacts the secret, so a later public export looked harmless, while `to_string_with_secret()` still contained the WIF. Extended private keys (`xprv` / `tprv`) were already rejected. A watch-only import of a WIF would have placed a spendable key on the agent host.

**Fix.** Import rejects a WIF-shaped string and rejects any descriptor whose secret form differs from its public form. Confirmed offline with a WIF derived from the public BIP39 abandon mnemonic on testnet. The WIF is not stored in the repository.

## Medium

### M1 — Chain URL fetchers followed redirects and accepted unexpected schemes

**CWE-918.** There is no webhook. The chain clients (`urlopen` in the Bitcoin fee fallback, EVM, XRP, Litecoin, and the registry) were the request surface. `urllib.request.urlopen` follows redirects and will open `file:` and other schemes. EVM and XRP already required https; the other callers did not share that check.

**Fix.** `validate_chain_url` plus `open_chain`. Allowed: `https`, or `http` only for `localhost`, `127.0.0.1`, and `::1`. Mainnet is https only. Userinfo is rejected. Link-local, multicast, unspecified, and metadata hostnames are rejected. Redirects raise. `https` to an RFC1918 address stays allowed so a self-hosted node works.

### M2 — The spend ledger was an unsigned JSON list

Anyone who could write the data directory could lower the recorded total or backdate timestamps and reset the 24-hour cap without knowing the approval secret.

**Fix.** When an approval secret is configured, the ledger and pending state are sealed with HMAC-SHA256 over a domain string and canonical JSON. A bad MAC fails closed. A legacy unsigned list is rejected once a secret is set; it is not auto-sealed (an attacker could swap in an empty list and have it signed). Domain strings are `wallet|{coin}|{network}|ledger|state` and `btc|{network}|ledger|state`. This seal is the full digest, not the 12-hex approval code.

**Residual.** Deleting `ledger.json` still looks like a new wallet and starts a fresh window. A process that can delete that file on the server user's account can usually read the approval secret as well. An external anchor would be needed to tell "new wallet" from "deleted ledger". That anchor was not added.

### M3 — Seed ciphertext used one AAD for every coin, and scrypt `n` was unbounded

**CWE-345** for the swap. AES-GCM additional authenticated data was `btc-wallet-mcp:v1` for every file, so a ciphertext written for one coin could be decrypted as another if the attacker could replace the file. `n` was taken from the file with no upper bound, so a hostile file could make decryption do an arbitrary amount of scrypt work.

**Fix.** New files take an optional context (`btc`, or `{coin}:{role}`) mixed into the AAD. Decryption tries the context AAD, and falls back to the legacy AAD only when the caller passed no context or the file has no `context` field. `n` must be a power of two in `[2^10, 2^20]`. Production writes still use `N=2^17`. Tests use `2^10`.

**Residual.** Files written before this change have no context and still open with the legacy AAD, so those specific files can still be swapped. Re-saving them under the new context closes that.

### M4 — `format_amount` used floating point

`(10**18 + 3) / 1e18` displays as `1.0`. The approval screen prints the integer base units as well, but the parenthetical coin amount could disagree with the integer the human is approving. For wei, that is a displayed value off by more than dust.

**Fix.** Formatting uses integer `divmod`. `format_amount("eth", 10**18 + 3)` is `1000000000000000003 wei (1.000000000000000003 ETH)`.

### M5 — CI did not match the Scorecard checks that can live in the repo

`actions/checkout@v4` and `actions/setup-python@v5` were floating tags. Workflows had no `permissions` block. There was no SAST, pip-audit, gitleaks, or Dependabot.

**Fix.** See `.github/workflows/ci.yml`, `.github/workflows/security.yml`, and `.github/dependabot.yml`. SHAs: checkout `11d5960a326750d5838078e36cf38b85af677262`, setup-python `a26af69be951a213d495a4c3e4e4022e16d87065`. Gitleaks binary sha256 `a65b5253807a68ac0cafa4414031fd740aeb55f54fb7e55f386acb52e6a840eb`. Semgrep is installed with pip in the SAST job (`semgrep==1.181.0`) and that job does not install the project, so semgrep's own dependency tree is not the wallet environment. CodeQL was not added: the default configuration wants `security-events: write`, which this workflow avoids.

## Low

| Id | Issue | Fix |
|---|---|---|
| L1 | `hmac.compare_digest` raises `TypeError` when both strings have the same length and one is non-ASCII (Python 3.12). That was caught as a generic broadcast failure and did not increment the lockout counter. A shorter wrong code already counted. | `constant_time_equals` returns false for unequal types or lengths and for any compare error. A 12-character non-ASCII code now counts as a failure. |
| L2 | The Bitcoin-only policy did not reject a negative or non-integer fee. | Fee checks match the multi-coin policy. |
| L3 | `mkdir(parents=True)` left newly created parents at the process umask. | `ensure_dir` sets each created directory to `0700`. |

| L5 | The configure UI did not check `Host` or `Origin` and sent no security headers. | `Host` must be `127.0.0.1` or `localhost` with the bound port. `Origin`, when present, must match. Responses set `nosniff`, `no-referrer`, `no-store`, and a CSP of `default-src 'none'`. |
| L6 | The old range `mcp>=1.2,<2` allowed mcp 1.29.0 (CVE-2026-59951). | Floor is `mcp>=1.30,<2`. The CVE is stateful Streamable HTTP only. This server uses stdio, so the finding is not exploitable on the current transport. The floor is still raised. |

## What stays open

These were not given a code fix. They are either outside the repository, out of scope, or a residual of a fix above.

- **Branch protection** is a GitHub setting: required reviews, required status checks (`tests` and `security`), no force-push to `main`.
- **Signed releases / SLSA provenance.** No maintainer signing key was available. Nothing was signed.
- **Hash-pinned Python dependencies.** Ranges remain. Dependabot and `pip-audit .` in CI are the control.
- **Full-tree `mypy --strict`.** `bdkpython` and `embit` are untyped, and the rest of the tree has a large number of missing annotations. Strict mode is enabled for `src/btc_wallet_mcp/guard.py` only, and that file is clean.
- **Container and install script.** Later `main` added `deploy/Dockerfile` (non-root user) and a compose file with `read_only: true`, plus `scripts/install.sh` (dedicated OS user, secret file mode `0400`). The compose file does not set `cap_drop`. Those files were not part of the original review.
- **Hardware signing** on later `main` is an owner TTY command (`hw-sign`), not an MCP tool. The original review did not cover the device classes.
- **XRP destination tags** were missing at `80fdd63`. Later `main` binds a tag into the approval HMAC and refuses known exchange addresses without one. That gap was closed by that work.
- **Two prepared EVM transactions can share a nonce.** The human approves each one. This is not a hidden second spend, but approving both can make one of them fail or replace the other.
- **Approval codes are 12 hex characters (48 bits) of HMAC-SHA256.** Online guessing is bounded by the five-failure lockout. Lengthening the code would break the human protocol. Left as-is.
- **Ledger deletion** and **legacy seed files** as described under M2 and M3.
- **Same-OS-user compromise** remains total: `/proc/<pid>/environ` exposes the passphrase and the approval secret. The threat model already says the server user and the agent user must differ.
- **Semgrep `0o700`.** Suppressed as a false positive. Do not change those modes to `0644`.

## Controls that already held

Constant-time compare for equal-length ASCII codes. Mainnet opt-in phrase `I_UNDERSTAND_REAL_MONEY` (`BTC_WALLET_ALLOW_MAINNET` for the Bitcoin-only server). Cold `execute` refusal. The gate's `SpendAuthorization` seal is a private object, not an adapter argument. Limit ceilings require `limits_mac`. The configure UI has a CSRF token. Seeds are not returned by MCP tools. Gitleaks found no secrets in history or in the working tree.

## Tooling other than the four reports

- **mypy --strict** on `src/btc_wallet_mcp/guard.py`: success. Project-wide strict was not applied (see above).

## Verdict

No critical issue. The three high issues and the five medium issues have a fix in this branch. What remains is operational (branch protection, separate OS users, signed releases) or an accepted residual (deleting the ledger, legacy seed files, 48-bit codes). Treat the hot wallet as losable funds until an external auditor has reviewed the gate, the keystore, and the adapters.
